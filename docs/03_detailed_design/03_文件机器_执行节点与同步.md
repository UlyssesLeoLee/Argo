# 文件归属、执行节点与同步详细设计

## 两个互不混淆的主体

`file_owner_node`：被修改的源文件在哪台机器；`executor_node`：哪台机器运行 AI CLI。UI 必须把机器→仓库→路径嵌套显示，把执行节点单列。数据由 `context.argo_file_owner`、`context.argo_file_scope`、`target_node`、`repo_alias` 表达。

## 当前允许矩阵

| 文件任务 | 执行机器 | 行为 |
|---|---|---|
| 无仓库 / 纯聊天 | 任意允许节点 | 允许；任务不承诺修改文件 |
| 有仓库、路径在A | A | 允许；由 A 上映射的仓库建立独立 Worktree |
| 有仓库、路径在A | B | **拒绝**；不能误把 B 上同名路径当作 A 的文件 |
| 有仓库，试图 `../` 或绝对路径 | 任意 | **拒绝** |

## Worker 文件操作

1. 读取 `ARGO_REPOS` 白名单别名→绝对源目录。
2. `git worktree add --detach` 建立任务独立工作空间。
3. 按 `argo_file_scope` 使用 canonicalize 检查子目录归属；只将 CLI 的 `cwd` 调整到指定目录。
4. CLI 产物按 SHA-256 上传 Blob；Git 修改以 `git diff --binary` 导出为 patch 供审核。
5. 真实回写、合并、远端同步及路径级强制隔离尚未实现，不能把“作用路径提示”宣传为安全沙箱。

## 后续跨机写回协议（详细但未实现）

- 文件机 A 创建带 hash/commit 的只读快照，并签发按任务授权的时效性下载令牌。
- Worker B 在本地受限沙箱修改快照，回传包含 source_hash/base_commit 的 patch 与测试工件。
- Controller 对文件机 A 发起校验与审核请求，A 进行版本比较、冲突检测、人工审批后原子应用。
- 任一检查失败保持修改在隔离分支，不自动覆盖 A 文件；全程审计可追溯。

以上是为未来多机扩展预留的接口方向，并非本次已实现的同步能力。
