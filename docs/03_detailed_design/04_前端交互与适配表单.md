# Argo 详细设计：前端信息架构与交互

ID：ARGO-DD-004 · 版本：1.0

## 设计原则

以「平台、用户输入、附加参数、任务发出」为最短主路径；不让 Multica 的 Project/Issue 表单污染 Claude 的输入。统一界面尊重平台的语义差异，不强迫所有平台都变成原始 Prompt 聊天。页面视觉采用深蓝控制台，明亮黄绿行动色，清晰层级，细线边框；不依赖商业字体，系统字体自动回退。响应式断点约 1240/860/600px。

## 页面与交互组件

| 页面 | 组件 | 数据接口 | 状态 |
|---|---|---|---|
| Compose | Provider 6 卡、Prompt/Title、模型、节点、Repo | providers, nodes, tasks | 表单有效/无效/提交中 |
| Compose/Orca | Repo datalist、内部 Agent select | catalog task via Orca CLI | waiting/loading/selected |
| Compose/Multica | Workspace ID、新建/已有 Issue、Project/Agent datalist | catalog task via Multica CLI | waiting/loading/selected |
| Runs | 任务列表、状态过滤、详情、事件控制台 | tasks/events | queued/running/terminal |
| Runs/Artifacts | SHA 文件列表、下载按钮 | blob API | available/404/error |
| Nodes | 在线节点卡片、Provider 标签、仓库、并发 | nodes | online/offline |
| Settings | Token/session、Demo 状态、API 地址 | providers/health | disconnected/connected/demo |

## UI 关键行为

- 首次打开时界面可浏览，但没有 Token 不向真实 Controller 发送私有请求。
- 切换 Provider 时，保留统一标题/Prompt；清空不相关平台专属输入区域。
- 从 CLI 查询 catalog 时通过隐藏的元数据查询任务完成，结果转为 datalist；仍保留人工 ID 输入以适配不同版本 JSON 结构。
- 发送前校验本地表单和候选 Worker，后端再次校验；提交后转入对应任务详情。
- 默认轮询周期 3.5 秒；单任务日志通过 `since=<last_seq>` 递增读取，单次最多 200 行。
- 取消任务二次确认；对 terminal state 隐藏取消按钮。
- 结果文件使用 JS fetch 的 Authorization Header + Blob URL 下载；不能把 Token 附加到 URL query 参数。
- 所有动态外部字符串统一 HTML escape；stdout/stderr 使用 DOM `textContent` 避免 HTML 注入。
- `?demo=1` 明确 DEMO 标识，模拟数据不发送到生产 API；仅用于无环境视觉/流程验证。

## 可用性与后续优化

当前 Demo 模式是模拟任务执行回执，生产模式 UI 不会假装已完成。后续建议增加 Provider CLI 本机探测版本、任务参数预览、Multi-Turn Session/ACP、轮询改推送、成本统计和对 `dispatched` 的原平台状态追踪。按 IPA 的 IT/ST 必须在 Windows/Edge、Chrome、至少一种移动浏览器真实验收。

## 交互约束补充

- Orca 与 Multica 使用各自仓库/任务卡上下文，不显示可编辑的 Argo 本地 Worktree 仓库别名，`repo_alias` 固定为空。
- Orca / Multica 的模型由目标平台 Agent 配置控制，统一模型输入框禁用以防误导。
- 已有 Multica Issue 模式必须填写 Issue ID；不允许因漏填而静默新建任务卡。
- 首版 Worktree 仅隔离 Git 工作目录，并非操作系统级安全沙箱；前端策略名称明确说明这一点。
