# Argo 详细设计：六大平台适配器契约

ID：ARGO-DD-002 · 版本：1.0 · **所有执行命令应运行在选中的 Worker 节点上**

> 截至 2026-11-05 公开文档核验；升级 CLI 后须重新执行 IT。各命令 argv 由 Rust `model.rs::invocation` 创建，不通过 Shell 拼接 Prompt。

## 1. 适配矩阵

| Provider | 参数形式 | 运行模式 | Argo 终态 | 本地授权前提 |
|---|---|---|---|---|
| Claude | `claude -p PROMPT --output-format stream-json [--model MODEL]` | one-shot JSON stream | completed/failed | 已登录 Claude Code |
| Codex | `codex exec --json --sandbox workspace-write --skip-git-repo-check [--model MODEL] PROMPT` | one-shot JSONL | completed/failed | 已登录 Codex |
| Hermes | `hermes chat --query-file PATH --oneshot [--model MODEL]` | one-shot File input | completed/failed | 已登录 Hermes |
| MiniMax | `mcode exec PROMPT [--model MODEL]` | one-shot CLI | completed/failed | 已登录 MiniMax / 已配置 provider |
| Orca | `orca worktree create --repo id:REPO --name argo-ID --agent AGENT --prompt PROMPT --json` | 异步启动 Agent | dispatched/failed | Orca CLI 注册、App/Server 运行 |
| Multica | `multica --workspace-id WS issue create --title TITLE --description-file PATH --project PROJECT --assignee AGENT --output json` | 异步 Issue 派发 | dispatched/failed | CLI 登录、Workspace 权限/Daemon |

`[--model MODEL]` 为可选，MiniMax 的模型 ID 应是其已配置的 provider/model 标识。Orca 的模型由其内部 Agent 设置控制；Multica 使用工作空间内 Agent 对应的模型与 Runtime 配置，本版 UI 不再额外传不被原平台识别的模型参数。

## 2. Claude Code

CLI Prompt 和 `--output-format stream-json` 按平台原生形式传递；stdout 是结构化行的原始流，Argo 第一版不对模型内部事件做语义重构。Provider 自己的权限/沙箱控制依赖本机配置；Argo 不默认使用危险的跳过授权参数。

来源：https://code.claude.com/docs/en/headless （官方 Claude Code headless 文档）

## 3. Codex

使用 `exec` 的非交互模式；`--json` 输出增量事件；`--sandbox workspace-write` 限制写入范围。Argo Worker 自己提供独立工作区；加 `--skip-git-repo-check` 允许纯任务目录。用户配置模型名称透传为 `--model` 参数。

来源：https://learn.chatgpt.com/docs/cli/reference

## 4. Hermes

长 Prompt 写入任务独立的 `prompt.md`，使用 `hermes chat --query-file <path> --oneshot`。相比把全部内容放进命令行，可避开大输入长度与 quoting 问题。模型通过 `--model` 覆盖单次运行。Hermes 可能共享其 HOME 下的状态文件，多任务并发写同一 Profile 有覆盖风险；未来需配置独立的 Hermes Profile 或 HOME 目录隔离。

来源：https://github.com/NousResearch/hermes-agent/blob/main/website/docs/reference/cli-commands.md

## 5. MiniMax Code

执行 `mcode exec "prompt"`；已配置 provider 时支持 `--model provider-id/model-id`。MiniMax CLI 也支持 ACP（`mcode acp`），但本期采用已记录的 exec 一次性执行；ACP 交互、权限请求卡片与续聊为二期。

来源：https://github.com/MiniMax-AI/minimax-code 及 https://github.com/MiniMax-AI/minimax-code/blob/main/docs/examples.md

## 6. Orca

Orca 不等于模型本身，而是 Agent 开发环境；在 Worker 节点通过 `orca repo list --json` 取得仓库，选择 `orca_repo_id` 与 `orca_agent`，然后调用 `orca worktree create --repo id:… --name … --agent codex|claude|… --prompt … --json`。不使用不确定的终端交互命令模拟输入。CLI 返回成功只说明创建/派发成功，不自动映射为模型完成。

来源：https://www.onorca.dev/docs/cli/reference

## 7. Multica

创建新任务卡：

```text
multica --workspace-id WS issue create
    --title TITLE --description-file PROMPT_FILE
    --project PROJECT --assignee AGENT --output json
```

已有任务卡：

```text
multica --workspace-id WS issue comment add ISSUE --content-file PROMPT_FILE --output json
multica --workspace-id WS issue assign ISSUE --to AGENT
```

先追加内容再赋予对应 Agent 运行机会。两个命令不是事务；若评论成功而指派失败，则 Argo 标记失败并展示部分成功事实，禁止自动再次发送评论。Project、Agent、Issue 可分别通过 `project list`、`agent list`、`issue list --project …` 的 JSON 结果为 UI 提供选择器；原生 Workspace ID 通过全局 `--workspace-id` 传递。

**重要：** Multica 可能具有自己的远程调度、任务重试和额外账单，Argo 的 `dispatched` 不保证该项目的后台 Agent 已真正开始或最终完成。

来源：https://github.com/multica-ai/multica/blob/main/apps/docs/content/docs/cli.mdx 与 https://github.com/multica-ai/multica/blob/main/CLI_AND_DAEMON.md

## 8. 统一约束与不支持项

- 每个平台必须先安装 CLI、登录并通过该平台的自身授权；Argo 从未上传 Agent 的 API Key。
- 无法确认的参数一律不自动传递。模型参数不跨平台拼凑使用。
- 安装与认证错误不得被静默改为成功；所有参数数组都经 Rust `Command::args`，不经 `cmd /C` 或 `bash -c`。
- 每个平台的返回码语义可能因版本改变；升级需要安装版本核验和端到端验收，不能只依赖编译成功。
