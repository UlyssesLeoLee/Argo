# 详细设计：AI 预处理、批量统一规则与历史恢复

## 处理步骤

1. 用户明确选择片段、当前筛选或全库，填写统一要求、模型、Provider、API Key。
2. Controller 读取每批最多 8 条，脱敏并截取每条最多 2500 Unicode 字符。
3. `POST /api/v1/ai/preview` 发出 OpenAI-compatible chat/completions HTTP；仅支持固定厂商 URL 或管理员预设的 HTTPS 自定义 URL。
4. 验证返回 JSON `items[]` 的 ID 唯一匹配、数量、title/content/tags/summary 长度，无效则整批失败。
5. UI 展示样例差异与总数，用户点击确认（必要时操作系统原生确认）；后续批次自动按相同规则处理。
6. `POST /api/v1/ai/apply` 在 SQLite 事务中写入旧快照到 `rag_ai_revisions`，CAS 检查旧 `revision`，更新 title/content/summary/tags 和 fingerprint；状态设 draft，remote_id 清空。事务部分失败整批回滚。
7. 执行后人工验证，单独批准并同步目标连接器；不自动覆盖远端知识。
8. `GET /api/v1/ai/revisions/{id}` 返回历史元数据；`POST /api/v1/ai/revisions/{id}/restore` 需 confirm，恢复为 draft，并把恢复前版本另存为快照。

## 输入/输出约定

```json
{ "ids": ["rag-01"], "operation": "tags", "instructions": "统一标签", "provider": "openai", "model": "model-id", "api_key": "TRANSIENT_SECRET" }
```

响应 `{operation, changes:[{id, revision, title, content, summary, tags}], preview_only:true}`。

## 安全/成本/一致性

- 仅管理员 Token 可调用本机 API；跨机使用 TLS 反代/VPN。Key 仅进请求、内存与第三方模型服务，不能写 DB、日志、RAG 片段。
- 单次模型请求 8 条；全库大批处理时成本可能较高，需要显示数量并显式确认。UI 最多收集 50,000 条，失败可人工恢复/续跑。
- Batch 实现在客户端，关闭桌面窗口就中断，因此属于 MVP 非持久作业，不应宣称具备服务器可恢复队列。
- 正则脱敏只是基础防线，识别不出所有敏感项。对用户提示词和模型输出做边界处理，审查并不保证不出现幻觉。
